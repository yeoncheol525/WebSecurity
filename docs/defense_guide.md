# 방어 가이드 · MiniShop

핵심 원칙: **보안기능을 적용했다는 사실만으로 방어 성공이 아니다.**
같은 공격을 방어 전/후에 재수행하고, 패킷·로그·응답·시스템 상태로 차단을 **실증**한다.
또한 방어가 **정상 기능**을 깨지 않는지 함께 확인한다.

## 방어 요소와 입증 포인트

| 방어 | 적용 지점 | 비교 조건 | 확인할 증거 | 취약점 |
|---|---|---|---|---|
| D1 쿼리 바인딩 | Catalog 검색값을 SQL과 별도 인자로 전달 | E1↔E2, E3↔E4 | 구조 변조 마커 소멸, 비공개 노출 0, 정상 작은따옴표 검색 유지 | CWE-89 |
| D2 DB 최소 권한 | Catalog를 `catalog_reader`로 연결 | E1↔E3, E2↔E4 | E3에서 `SQLSTATE 42501`, 외부 노출 0, 공개 검색 유지 | CWE-89 피해 제한 |
| D3 객체별 인가 | 세션 user_id와 주문 소유자 대조 | C2(off) ↔ E4(on) | 타인 주문 본문 소멸, 본인 주문 정상 | CWE-639/862 |
| D4 감사/탐지 | request_id·DB 이벤트 기록 | 동일 공격/정상 집합 | 경고 발생과 **응답 전 차단**을 구분 기록 | — |

## 왜 막히는가 (조건별 설명)

- **E2 (바인딩 ON):** 입력이 SQL 구조가 아닌 **검색 문자열 값**으로 처리된다. UNION 구문이 통째로 상품명 검색어가 되어 매칭 0건. → D1이 *취약점 자체*를 예방.
- **E3 (최소 권한 ON):** SQLi 구문 변조는 여전히 일어나지만, `catalog_reader`에 `private`/`auth` 스키마 USAGE·SELECT 권한이 없어 DB가 `42501 permission denied`로 거부. → D2는 *피해 범위*를 제한(취약점은 남음).
- **E4 (이중):** 웹에서 1차 차단(바인딩), 만약 뚫려도 DB에서 2차 차단(권한). 가장 이상적.
- **A 로그인 (바인딩):** username이 값으로 바인딩되어 `' OR '1'='1' --`가 존재하지 않는 사용자명으로 조회→행 없음→401. 세션 미발급.
- **C2 → 소유자 검사(D3):** 바인딩과 **무관**하다. 쿼리가 안전해도 `WHERE c.user_id = 세션` 인가가 없으면 타인 주문이 반환된다. 바인딩(D1)과 인가(D3)는 서로 다른 목적임을 보이는 지점.

## 측정 단위와 계산식

| 지표 | 정의 |
|---|---|
| 고객정보 노출량 | 응답에 포함된 **고유** customer_id 수(중복 제외), 분모 100 |
| 공격 성공률 | 노출 기준 충족 시퀀스 / 전체 유효 시퀀스 |
| 정상 기능 유지율 | 정상 검색·로그인·본인 주문 성공 수 / 예정 수 |
| 응답 지연 | 기능별 median/p95 (`p95 = ceil(0.95·n)`번째) |
| 탐지율/오탐률 | 자동 탐지 규칙 **미구현 → N/A** (D4는 로그 수집까지만) |

## 판정 원칙

1. HTTP 200만으로 노출 성공, 오류 응답만으로 방어 성공이라 하지 않는다.
2. 노출 "성공"은 비로그인 응답에 합성 `private.customer_id`가 1건 이상 포함될 때만.
3. 방어 "성공"은 같은 입력에서 노출 0 **이고** 그 원인(바인딩/권한거부/인가거부)이 로그·코드·권한으로 설명될 때만.
4. 모든 방어 조건에서 정상 기능(공개 검색, 로그인, 본인 주문)이 유지되는지 반드시 함께 기록.
5. 예상값(Dummy)과 실측값을 표에서 구분한다.

## 권장 절차

취약점 분석 → 공격 시나리오 → ATT&CK 매핑 → 공격 구현·검증 → D3FEND 방어 적용 → **동일 공격 재검증** → 정량 평가 → 결과 분석.

매핑: CWE-89(SQLi)·CWE-639/862(인가) · ATT&CK T1190, T1213.006 · D3FEND D3-AMED(접근 매개), D3-DQSA(쿼리 분석).
