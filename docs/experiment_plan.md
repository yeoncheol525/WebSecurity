# 팀 실험 진행과 제출물 안내

조건 설정: [E1](../experiments/E1/README.md) · [E2](../experiments/E2/README.md) ·
[E3](../experiments/E3/README.md) · [E4](../experiments/E4/README.md).

E1~E4 설정과 방어 예제 구현을 출발점으로 사용한다. 입력 집합·판정 기준 확정,
반복 측정과 단계별 방어 효과 분석은 팀원이 직접 수행한다. 설치나 회귀 검사 통과를 아래 결과표에 옮겨 적지 않는다.

## 목표와 현재 범위

합성 고객·주문·결제 메타가 공개 검색 응답에 노출되는지 관측하고, 검색 바인딩과 DB 최소 권한이 주는 차이를 설명한다.
노출 여부와 방어 효과는 실제 HTTP 응답·같은 request_id의 로그·코드·DB 권한을 근거로 판정한다.
현재 준비된 것은 실행 환경과 네 조건의 코드다. 실제 노출 재현·반복 측정·분석·영상은 담당 팀원의 작업이다.

| 항목 | 현재 범위 |
|---|---|
| E1~E4 | 상품 검색의 바인딩 × Catalog DB 조회 권한 비교 |
| 로그인·본인 주문 | 모든 조건에서 유지되는 정상 기능 |
| 주문 소유자 검사 | E1~E4에서 적용. OFF/ON 비교는 보조 실험 C2로 제공 |
| 고객정보·배송지 변경 | 수정 API와 검색 계정의 변경 권한 없음 |
| 감사 로그 | 증거 수집용. 자동 탐지율·오탐률은 `N/A` |

## 시작 전에 담당자가 작성할 것

환경 담당은 실행 commit·서버 주소·시드 버전을 전달한다. 실험 담당은 아래 양식을 작성하고,
방어 담당과 함께 각 항목의 판정 기준을 검토한다. 이름은 팀에서 배정받은 담당자로 기입한다.

| 항목 | 담당자 작성 내용 |
|---|---|
| 환경 / 실험 / 방어 / 통합·발표 담당 | 이름 기입 |
| 실행 commit·시드·서버 주소 | 직접 확인해 기입 |
| 실험 입력 목록 | 입력 ID별 원문과 평가 목적 기입 |
| 성공·실패·판정 불능 기준 | 어떤 응답·노출 ID·로그를 근거로 판정할지 기입 |
| 반복 횟수·타임아웃·요청 간격 | 네 조건에 공통으로 적용할 값 기입 |
| 결과 폴더·영상 파일명 | 팀 실행명을 정해 기입 |

입력 목록 양식:

| 입력 ID | 구분 | 입력값 | 확인할 내용 | 반복 횟수 |
|---|---|---|---|---|
| N01 | 정상 검색 | `Notebook` | 공개 상품 검색 | 담당자 기입 |
| N02 | 정상 검색 | `NoSuchProduct` | 검색 결과 없음 | 담당자 기입 |
| N03 | 정상 검색 | 빈 검색값 | 공개 상품 전체 목록 | 담당자 기입 |
| N04 | 정상 검색 | `O'Reilly` | 작은따옴표가 포함된 정상 상품명 | 담당자 기입 |
| A01 | 팀 설계 실험 | 담당자 작성 | 평가 목적·판정 기준 작성 | 담당자 기입 |

필요한 실험 항목은 A02, A03처럼 추가한다. 이 문서에는 완성된 공격 입력을 제공하지 않는다.
담당자가 작성한 입력 목록과 판정 기준을 먼저 확정한 뒤, 모든 조건에 같은 목록을 적용한다.

## 진행 순서

1. **환경 담당:** [설치 안내](TEAM_SETUP.md)에 따라 서버를 준비하고, 참여자에게 주소·조건·웹 계정을 전달한다.
2. **실험 담당:** 아래 정상 검색 기록으로 접속·정상 기능부터 확인한다. 예상값과 다른 항목은 원인을 기록한다.
3. **환경 담당:** 조건을 선택하고 `/health/catalog`의 실제 `database_role`·`query_mode`를 전달한다.
4. **실험 담당:** 확정한 입력 목록에 따라 관측하고, 입력 ID·조건·요청별 응답·시간·request_id·화면 캡처를 기록한다.
   앞 조건의 기록을 마친 뒤 다음 조건으로 전환하며, 입력 목록과 반복 기준을 유지한다.
5. **방어 담당:** 코드·DB 역할/권한·같은 request_id의 로그를 대조해 응답 차이의 원인을 설명한다.
   데이터가 보이지 않았다는 사실만으로 방어 성공으로 판정하지 않는다.
6. **전원:** 정상 검색·로그인·본인 주문 결과를 함께 검토하고, 아래 조건별 결과표와 제출물을 완성한다.

실험 종료 후 환경 담당은 E4로 복귀한다. 입력이나 판정 기준을 수정했다면 변경 이력을 남기고,
조건 간 비교에 사용한 입력 집합이 같은지 다시 확인한다.

## 정상 검색 기록

처음 접속했다면 [실제로 무엇을 입력하나](../README.md#실제로-무엇을-입력하나)의 네 검색값부터 확인한다.
E1에서 아래 네 행을 기록한 뒤 E2·E3·E4에도 같은 네 행을 추가한다.

| 조건 | 검색 입력 | HTTP 상태 · 실측 | 상품 수 또는 오류 · 실측 | X-Request-ID |
|---|---|---|---|---|
| E1 | `Notebook` | 미측정 | 미측정 | |
| E1 | `NoSuchProduct` | 미측정 | 미측정 | |
| E1 | 빈 검색값 | 미측정 | 미측정 | |
| E1 | `O'Reilly` | 미측정 | 미측정 | |

이 표는 정상 기능 확인용이다. 아래의 공격·방어 실험 결과표와 별도로 기록한다.
공격 실험용 공통 입력 집합과 성공 판정 기준은 별도로 확정해야 한다.

## 비교 조건

| 비교 | 변경 요소 | 고정 요소 |
|---|---|---|
| E1 ↔ E2 | 검색 바인딩 | wide DB 역할 |
| E3 ↔ E4 | 검색 바인딩 | 최소 권한 DB 역할 |
| E1 ↔ E3 | DB 권한 | 문자열 삽입 검색 |
| E2 ↔ E4 | DB 권한 | 바인딩 검색 |

- 시드·입력 집합·반복 횟수·타임아웃·요청 간격 고정.
- 실행 commit과 조건 기록.
- 조건 전환 전 진행 중인 요청 종료.
- 검색 구조 변경과 HTTP 응답의 비공개 데이터 노출을 별도 기록.
- HTTP 상태 코드와 같은 request_id의 오류 원인 함께 확인.
- HTTP 200만으로 노출 성공, 오류 응답만으로 방어 성공이라고 판정하지 않는다.
- 정상 검색·로그인·본인 주문 결과 포함.
- E1·E3의 작은따옴표 정상 검색 실패도 정상 기능률에 반영.
- 로그인·주문 인가는 모든 조건에서 동일하게 유지.

## 기록 항목

1. 실행 시각, commit, 조건, `/health/catalog`의 DB 역할과 query_mode.
2. 입력 집합, 요청별 `X-Request-ID`, 상태 코드, 응답 본문, 소요시간.
3. 같은 request_id의 서버 감사 로그와 화면 캡처.
4. 고유 고객·주문·결제 메타 ID 수.
5. 정상 기능 성공 건수와 기능별 지연.

요청·응답 관찰: **Burp → Proxy → HTTP history → 요청 선택 → Request / Response**.
정상 요청 재전송: **정상 검색 요청 우클릭 → Send to Repeater → Send**.
브라우저 F12는 화면·네트워크 보조 확인에 사용한다.
설정은 [Burp 사용 순서](../README.md#브라우저-사용--kali-desktop--windows)를 따른다.

서버 로그 · Ubuntu:

```sh
sudo docker compose logs --tail 100 catalog-service order-service
```

## 판정 기준

- 데이터 분모: 고객 100명, 주문 300건, 결제 메타 300건.
- 노출량: HTTP 응답에 포함된 고유 ID 수. 중복 ID 제외.
- 공격 성공률: 사전에 정의한 노출 기준을 충족한 유효 시퀀스 / 전체 유효 시퀀스.
- 주문·결제만 노출된 경우도 별도 피해로 기록.
- 오류·타임아웃·판정 불능은 원인별 기록.
- 정상 기능률: 정상 요청 성공 건수 / 예정 정상 요청 건수.
- 지연: 검색·로그인·본인 주문별 median/p95.
- p95: 정렬 후 `ceil(0.95 × n)`번째 값.
- 자동 탐지 규칙 미구현: 탐지율·오탐률 `N/A`.
- 미측정 항목: `미측정`.

## 과제 제출물

기록 위치는 로컬 `results/<팀 실행명>/`로 정한다. 아래 파일은 실제 작업을 수행한 담당자가 작성한다.
빈 폴더나 결과 파일은 미리 생성할 필요가 없다.

| 제출 근거 | 포함할 내용 |
|---|---|
| 입력 목록 | 입력 ID·원문·목적·판정 기준·반복 조건 |
| 요청별 기록 | 실행 commit·조건·입력 ID·상태·관측 결과·소요시간·request_id |
| 캡처·로그 | HTTP 응답과 동일 request_id의 서버 기록, 실제 DB 역할·권한과 코드 근거 |
| 비교 결과표 | 네 조건의 실측값, 정상 기능, 지연, 오류·판정 불능, 측정 한계 |
| 시연 영상 | 실제 환경·관측 결과·조건별 방어 차이·정상 기능 유지·결과표 설명 |

기획서의 1~3분 영상은 다음 흐름으로 구성할 수 있다.

1. 실행 환경과 연구 질문, 정상 상품 검색을 보여준다.
2. 담당자가 실제로 관측한 합성 데이터 노출 여부와 응답 근거를 보여준다.
3. 조건별 코드·권한 차이와 관측 결과를 연결해 바인딩과 최소 권한의 효과를 각각 설명한다.
4. 정상 기능 확인, 실측 결과표와 한계를 정리한다.

로그인 후 본인 주문을 본 화면은 정상 기능 증거다. 비공개 정보 노출을 재현했다고 주장하려면
그 주장에 해당하는 실제 응답과 조건별 근거가 있어야 한다. 재현되지 않은 내용은 결과에 맞게 설명한다.
공유 자료에서는 비밀번호·Cookie/Set-Cookie·토큰을 제거한다.
