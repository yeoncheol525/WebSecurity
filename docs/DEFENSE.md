# 방어 원리와 판정 기준

보안 설정을 적용했다는 사실만으로 방어 성공이 아니다. 같은 공격을 방어 전·후에 재수행하고, 응답·로그·DB 권한으로 차단을 입증한다. 방어가 정상 기능을 깨지 않는지도 함께 확인한다.

## 방어 요소

| 방어 | 적용 지점 | 효과 / 한계 | 취약점 |
|---|---|---|---|
| D1 쿼리 바인딩 | 검색·로그인·주문 입력을 SQL과 별도 인자로 전달 | 구문 변조 **예방**. 객체 접근권한은 보장하지 않음 | CWE-89 |
| D2 DB 최소권한 | Catalog를 `catalog_reader`로 연결(`private` 권한 없음) | SQLi가 남아도 민감 테이블 접근 **거부(42501)** | CWE-89 피해 제한 |
| D3 객체 인가 | 세션 user_id와 주문 소유자 대조 | 정상 SQL을 통한 타인 주문 조회 차단 | CWE-639/862 |
| D4 감사 로그 | request_id별 binding·row_count·sqlstate·인가결과 기록 | 증거 수집. 자동 탐지 규칙은 미구현 | — |

## 조건별 차단 근거

- **E2(바인딩)**: 입력이 SQL 구조가 아닌 검색어 값으로 처리되어 UNION이 매칭 0건. 취약점 자체를 예방.
- **E3(최소권한)**: 구문 변조는 성립하지만 `private`/`auth` 스키마 권한이 없어 `42501`로 거부. 취약점이 남아도 피해 범위를 봉쇄.
- **E4(이중)**: 웹 1차(바인딩) + DB 2차(권한).
- **로그인(A)**: username이 값으로 바인딩되고 비밀번호 해시를 검증하므로 `' OR '1'='1'`가 401.
- **IDOR(C2)**: 바인딩과 무관하다. 쿼리가 안전해도 소유자 인가가 없으면 타인 주문이 반환된다. D1(예방)과 D3(인가)는 목적이 다르다.

주문정보는 두 독립 경로로 유출될 수 있다 — 과권한 SQLi(E1, D2로 차단)와 인가 결함(C2, D3로 차단). 한 방어가 다른 경로를 대신 막지 못한다.

## 지표와 판정

| 지표 | 정의 |
|---|---|
| 노출량 | 응답의 고유 `customer_id` 수(중복 제외), 분모 100 |
| 공격 성공률 | 노출 기준 충족 시퀀스 / 전체 유효 시퀀스 |
| 정상 기능 유지율 | 정상 검색·로그인·본인 주문 성공 수 / 예정 수 |
| 응답 지연 | 기능별 median / p95 |
| 탐지율·오탐률 | 자동 탐지 규칙 미구현 → N/A |

- HTTP 200만으로 노출 성공, 오류만으로 방어 성공이라 판정하지 않는다.
- 노출 성공: 비로그인 응답에 합성 `customer_id` 1건 이상.
- 방어 성공: 노출 0 **이고** 그 원인(바인딩/42501/인가거부)이 로그·코드·권한으로 설명됨.
- 예상값과 실측값을 구분한다.

매핑: CWE-89 · CWE-639/862 · ATT&CK T1190, T1213.006 · D3FEND D3-AMED, D3-DQSA.
